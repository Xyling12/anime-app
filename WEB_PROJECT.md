# AniPulse Web — проектный документ (архитектура веб-версии)

> Полное проектирование веб-версии приложения AniPulse. Дано: работающий Android-клиент
> (Kotlin/Compose) как эталон дизайна и логики, работающий бэкенд-шлюз на `anipulsetv.ru/alapi/*`,
> база пользователей и весь соц-функционал уже на сервере. Задача: спроектировать веб-клиент,
> который переиспользует существующий бэкенд.
> **Статус: проектирование. Код не начат.**
>
> **Решения владельца (18.07):** (1) SEO-трафик НУЖЕН → модель Next.js + ISR (публичное — статика
> для Google, приватное — CSR). (2) Сервер пока текущий (961МБ), масштаб — по мере роста
> (первым упрётся чат-поллинг → тогда WebSocket/SQLite). (3) Страницы Конфиденциальность и
> Для правообладателей ОБЯЗАТЕЛЬНЫ в каркасе (тексты уже готовы на сервере, переиспользуем).

---

## 0. Проверка осуществимости (сделана до проектирования)

**Критический риск — воспроизведение видео в браузере — СНЯТ.** Проверено на живом потоке:
CDN Kodik (`cloud.solodcdn.com`) отдаёт `Access-Control-Allow-Origin: *` на видео-сегменты.
Значит `hls.js` в браузере может тянуть сегменты **напрямую с CDN**, без прокси через наш VPS.

Последствие: **видеотрафик НЕ идёт через наш сервер** (иначе 961МБ-RAM VPS не выдержал бы
и десятка зрителей). Через шлюз идёт только извлечение m3u8-манифеста (уже реализовано,
лёгкий JSON-запрос). Это делает проект реалистичным.

Остаётся проверить при разработке: referer-защиту самого манифеста (шлюз уже её обходит
server-side) и стабильность CORS на всех качествах/озвучках.

## 1. Стек и обоснование

| Слой | Выбор | Почему |
|---|---|---|
| Фреймворк | **Next.js 14 (App Router) + TypeScript, режим ISR** | Публичные страницы (тайтл/каталог) генерируются как статика с периодной регенерацией → Google индексирует готовый HTML, а сервер НЕ рендерит на каждый запрос (бережём RAM). Приватное (плеер/чат/профиль) — CSR в браузере. |
| Стили | **Tailwind CSS** | Быстрое повторение дизайна Android, единая тема (тёмная/светлая — как в приложении). |
| Серверные данные | **TanStack Query (React Query)** | Кэш, дедупликация, поллинг чата/ЛС (заменяет ручные `while(true)` из Android). |
| Локальное состояние | **Zustand** | Тема, текущий юзер, том громкости — легковесно. |
| Плеер | **hls.js** + `<video>` | m3u8 напрямую с CDN. Кастомный оверлей управления поверх video. |
| PWA | **next-pwa** | «Установить на экран», офлайн-оболочка, ощущение приложения. Дёшево. |

Альтернатива Next → чистый **Vite + React SPA**, если решим отказаться от SSR/SEO
(например, из-за юр-рисков индексации). SPA проще хостить (статика + Caddy), но теряем
поисковый трафик. **Решение отложено до §9.**

## 2. Хостинг и инфраструктура

**Проблема:** VPS имеет 961МБ RAM, шлюз уже ест ~25МБ, но Next.js в SSR-режиме — это
ещё один постоянный Node-процесс (~80-150МБ) + сборка. Впритык.

**Варианты:**
1. **Статический экспорт Next (`output: export`) + раздача через Caddy** — 0 доп. RAM,
   но теряем SSR (SEO страниц тайтла). Каталог грузится клиентом. → **Рекомендуется для старта.**
2. **SSR на том же VPS** — нужен апгрейд тарифа (2ГБ RAM, ~+200₽/мес) ИЛИ вынести Next
   на отдельный дешёвый VPS, шлюз оставить где есть.
3. **Vercel (бесплатно)** — зарубежный хостинг: для РФ-аудитории латентность + риск
   блокировок + оплата не нужна. Как быстрый MVP годится, для прода — свой сервер.

**Caddy:** добавить блок для веб-раздачи (аддитивно, как делали с доменом). Веб на корне
`anipulsetv.ru/`, API остаётся на `/alapi/*`. Один домен, без CORS-проблем между фронтом и API.

## 4. Слой API (переиспользуем существующий бэкенд ПОЛНОСТЬЮ)

Всё уже готово на `https://anipulsetv.ru/alapi/`. Веб-клиент = новый UI поверх тех же эндпоинтов:
- Каталог/тайтлы: `shikimori/*` (прокси), `ratings`, `poster/{id}`.
- Видео: `kodik-find`, `kodik-dubs`, `kodik?link=&episode=` → m3u8 → hls.js напрямую с CDN.
- Таймкоды: `aniskip/*`.
- Аккаунты: `auth/register|login|me|forgot|reset|logoutall|verify`.
- Соц: `chat`, `comments`, `rating`, `dm/*`, `friends/*`, `notifications`, `user`, `profile`, `avatar`, `avatar-upload`, `avatar-img`.
- Эфир: `shikimori/api/calendar`, `anilibria-updates`.

**Клиент — тонкий типизированный слой** (fetch-обёртки + React Query hooks), TypeScript-типы
зеркалят Kotlin data-классы из `GatewayApi.kt`.

## 5. Что ТРЕБУЕТ доработки сервера (честный список)

Веб отличается от Android в трёх местах — понадобятся аддитивные правки шлюза:

1. **OAuth-callback для веба.** Сейчас `auth/vk|yandex/callback` редиректит на deep link
   `anipulse://auth?token=`. Для браузера нужен веб-callback: определять источник (по `state`)
   и редиректить на `https://anipulsetv.ru/auth/callback?token=...` (или ставить httpOnly-cookie).
   → небольшая правка `handleOAuthVk`/`handleOAuthYandex` + добавить веб-redirect_uri в кабинеты VK/Яндекс.

2. **Прогресс просмотра.** В Android хранится ЛОКАЛЬНО в Room (сервер о нём не знает!).
   В вебе два пути:
   - (a) `localStorage` — просто, но не синкается между устройствами;
   - (b) новый серверный эндпоинт `progress` (JSON-хранилище, как chat/dm) — синк везде,
     заодно улучшит и Android. → **Рекомендуется (b)**, это и Android апгрейд.

3. **Пуши в вебе.** Web Push (VAPID) работает без Google. ИЛИ проще — поллинг в открытой
   вкладке (React Query уже поллит). Для MVP — поллинг, Web Push позже.

Всё остальное (аккаунты, чат, аватарки, рейтинги) работает как есть, без правок сервера.

## 6. Плеер — ядро сложности (детально)

```
1. GET /alapi/kodik-dubs?shikimoriId=X   → список озвучек
2. Выбор озвучки → GET /alapi/kodik?link=<ref>&episode=N → { "720": "https://...m3u8", ... }
3. hls.js.loadSource(m3u8)  → сегменты тянутся напрямую с cloud.solodcdn.com (CORS *)
4. Оверлей поверх <video>: play/pause, сикбар с метками опенинга(жёлт)/эндинга(оранж),
   выбор качества (пересоздать hls на новом m3u8, seek на позицию), смена озвучки,
   кнопки ⏮⏯⏭ серии, «Пропустить опенинг» (AniSkip таймкоды), автопереход.
5. Прогресс: сохранять каждые ~5с (localStorage или сервер, см. §5.2), watched при >90%.
```

**Не переносится из Android:** жесты свайпом (яркость/громкость) — в вебе нет доступа к
яркости, громкость — через `video.volume`. Двойной тап ±10с — можно. Fullscreen API — есть.

**Safari/iOS нюанс:** iOS не даёт inline-HLS через hls.js напрямую в `<video>` в некоторых
случаях — Safari умеет нативный HLS, надо детектить и отдавать m3u8 в `src` напрямую.

## 7. Отличия веба от Android (что НЕ переносится 1:1)

| Функция | Android | Web |
|---|---|---|
| Пуши | WorkManager + локальные уведомления | Web Push (VAPID) или поллинг во вкладке |
| Прогресс | Room (локально) | localStorage или новый серверный эндпоинт |
| Аватарка-загрузка | PickVisualMedia + crop | `<input type=file>` + canvas-crop (проще) |
| Жесты плеера | свайпы яркость/громкость | нет яркости; громкость кнопкой |
| Deep link входа | `anipulse://` | веб-redirect ?token= или cookie |
| Хранение токена | EncryptedSharedPreferences | httpOnly-cookie (безопаснее) или localStorage |
| Ориентация плеера | форс-ландшафт | Fullscreen API + Screen Orientation (где поддержано) |

## 8. Этапы разработки (фазы)

- **Фаза 0 — каркас (1-2 дня):** Next+TS+Tailwind, тема, layout, навигация, API-слой + типы, деплой-пайплайн на VPS/Caddy.
- **Фаза 1 — просмотр без входа (3-5 дней):** Главная, Каталог (фильтры/поиск/жанры/бесконечная лента), страница тайтла, **плеер** (самое сложное), Эфир. Прогресс в localStorage. → уже полезный продукт.
- **Фаза 2 — аккаунты (2-3 дня):** регистрация/вход/сброс/верификация, OAuth VK/Яндекс (правка callback), Профиль, «Моё»/статусы, оценки.
- **Фаза 3 — соцчасть (3-4 дня):** чат, ЛС, друзья, уведомления, аватарки, комментарии, карточка пользователя.
- **Фаза 4 — полировка (2-3 дня):** PWA, адаптив (моб/десктоп), SEO-мета, синк прогресса на сервер, Web Push.

**Итого ~2-3 недели** плотной работы на MVP + полную соцчасть. Фазы 0-1 (~неделя) уже дают
рабочий сайт «зашёл-посмотрел».

## 9. Риски и стратегические вопросы (честно)

1. **⚠️ ЮРИДИЧЕСКИЙ — веб виднее и уязвимее APK.** Сайт со стримингом чужого аниме
   индексируется, легко находится правообладателями и **блокируется РКН по одному URL**
   (APK так не заблокировать). Это ГЛАВНОЕ отличие от Android-раздачи. Смягчение: не палить
   контент в SSR/индексации (тогда теряем SEO-смысл Next → берём SPA), домен-зеркала наготове,
   видео и так не на нашем сервере.
2. **RAM VPS** — SSR не влезет без апгрейда. Старт на статике/SPA.
3. **Kodik-механика** — та же хрупкость, что в Android (мониторинг уже есть).
4. **iOS/Safari HLS** — отдельная ветка кода для нативного HLS.
5. **Дубль поддержки** — теперь две кодовые базы (Android + Web) на одном бэкенде. Каждая
   новая фича — в двух местах.

## 10. Рекомендация архитектора

**Да, проект реализуем**, ключевой риск (видео) снят проверкой. Но:

- Начать со **статического SPA (Vite+React) или Next в static-export**, а не SSR — снимает
  и RAM-проблему, и часть юр-риска (не индексируем контент).
- **Один домен** `anipulsetv.ru`: `/` — веб, `/alapi/*` — существующий API. Без CORS-боли.
- Бэкенд переиспользуется на ~95%, правок сервера минимум (OAuth-callback + опц. прогресс).
- Реалистичный MVP «зашёл-посмотрел без установки» — **~неделя** (фазы 0-1).
- Полный паритет с Android (соцчасть) — **~2-3 недели**.

**Открытый вопрос к владельцу перед стартом:** SSR+SEO (больше бесплатного трафика, но выше
юр-видимость и нужен RAM) ИЛИ SPA (безопаснее и дешевле, но без поискового трафика)?
От этого зависит выбор Next vs Vite и хостинг.
